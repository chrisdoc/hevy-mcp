1. One endpoint policy module

Primary leverage Safety + locality
packages/hevy-client/src/hevy-client-kubb.ts packages/core/src/utils/hevy-error-policy.ts packages/core/src/utils/error-policy.ts packages/node/src/utils/hevy-client-observability.ts packages/operations/src/workouts.ts

Problem. Endpoint identity, retry meaning, expected 404s, safe diagnostic exposure, and metric normalization are encoded in separate lists across four shipped modules, so one upstream change can produce inconsistent behavior at several seams.

Direction. Establish one runtime-neutral endpoint policy module that records distinct policy facts without flattening them into one list. Core, Node, and operations consume those facts; unknown endpoints remain fail-closed and diagnostic redaction remains explicit.

Important constraint: preserve the current distinction between expected read misses and safe diagnostic paths; centralization must not broaden disclosure.

Benefits

  • One edit per endpoint
  • Fail-closed unknown endpoints
  • Safer diagnostic redaction
  • Stable metric dimensions
  • Policy tests gain leverage

4. Collapse Node lifecycle into one runner

Strong
packages/node/src/index.ts packages/node/src/utils/graceful-shutdown.ts packages/node/src/streamable-http.ts packages/node/src/index.test.ts

Problem. The stdio and HTTP paths separately construct process tracking, cancellation, run spans, configuration, startup metrics, update scheduling, shutdown, telemetry flush, and failure classification.

Direction. Extract one private Node lifecycle runner and keep stdio and HTTP as two transport adapters that contribute only transport setup and transport-specific observations.

Why this seam is justified

Two real adapters already repeat one substantial implementation; lifecycle bugs currently require parallel edits and tests.
