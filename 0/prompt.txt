## PR 1120 Review Findings Triage

**1. gitstream — cli/main.ts operations built from `createdClient` — REAL (medium)**
Evidence: `packages/cli/src/main.ts:55-63` — `const client = options.execution ? bindClientExecution(createdClient, options.execution) : createdClient;` then `context.operations = createOperations(createdClient, ...)`. The execution-bound proxy is only assigned to `context.client`; operations always get the raw client. The effect seam itself still works (the native-request-effect seam lives on the raw client and `getNativeRequestEffect` recovers it there), but operations calls lose the bound execution defaults (lifecycle signal, deadline, request binding) unless every call site threads `execution` options explicitly (which `runOperation` does for its own calls, but any options-less call bypasses binding).
Fix: pass `client` (the proxied client) to `createOperations` in `main.ts`.

**2. gitstream — scripts/measure-token-cost.ts deep effect import — VALID-NIT (hazard, low)**
Evidence: `scripts/measure-token-cost.ts:4` — `import { Effect } from "../packages/core/node_modules/effect/dist/index.js"`. Root `package.json` has no `effect` dependency, so this is a deliberate workaround for the workspace constraint (bare `import "effect"` would fail from `scripts/` under pnpm's isolated node_modules). It works today under tsx but creates a second Effect module instance relative to workspace packages and breaks if pnpm layout/hoisting changes.
Fix: add `effect` to root `devDependencies` and use a bare `import { Effect } from "effect"`.

**3. qodo — createToolRuntime ignores caller `createHandler` when `observer` set — REAL**
Evidence: `packages/core/src/tools/tool-runtime.ts:~269-296` — `const effectHandlerFactory = createHandler ?? (default withErrorHandling wrapper)` but `const observedHandlerFactory = observer ? createObservedHandler : effectHandlerFactory`. When `observer` is configured, `createObservedHandler` (which calls `withErrorHandling` directly) is used and the caller-supplied `createHandler` factory is never invoked.
Fix: have `createObservedHandler` delegate to the resolved `effectHandlerFactory` for the underlying invocation (or compose observer wrapping around `createHandler`).

**4. qodo — NetworkError loses request identity — REAL (minor)**
Evidence: `packages/hevy-client/src/effect-errors.ts:77-85` — `NetworkError` schema has only `code`, executionFields, retryCount/retryExhausted; no `method`/`endpoint`. `internal-request-effect.ts:~282-296` — `mapRequestError` computes `identity` (method/endpoint/page) but `networkError(cause)` (line ~283) doesn't receive or store it, so a statusless `HevyHttpError` collapses to a NetworkError with no request identity for safe diagnostics.
Fix: add optional `method`/`endpoint` fields to NetworkError and pass `identity` into `networkError()`.

**5. coderabbit — templates search vs listAll page_count divergence — REAL (low)**
Evidence: `packages/operations/src/templates.ts` — `createTemplatesSearchOperation` (~line 465-480) fails with `PaginationMismatchError` when `page_count` is missing/non-number; `createTemplatesListAllOperation` (~line 355-365) just passes `response?.page_count` to `hasNextTemplatesPage`, treating undefined as no-next-page → silent truncation. Inconsistent handling of the same upstream response shape.
Fix: share one pagination-validation helper so listAll applies the same page_count contract as search.

**6. coderabbit+gitar — workout update payload semantics — REAL (two parts)**
(a) Behavior change confirmed: origin/main `packages/core/src/tools/mutation-semantics.ts:281-286` always set `description: patch.description !== undefined ? patch.description : (current.description ?? null)`; the new `buildWorkoutUpdatePayload` (`packages/operations/src/mutation-semantics.ts:~382-396`) keeps `description = patch.description !== undefined ? patch.description : current.description` and only includes it `if (description !== undefined)`. So when both are undefined, main sent `description: null` (clearing) while the new code omits the field entirely (API may preserve existing description). Semantic difference on the PUT.
(b) Replacement branch confirmed: `packages/operations/src/workouts.ts:~424-431` — for a replacement patch, `current` is built from `patch.title/start_time/end_time` directly (no GET fetch, unlike origin/main which always fetched). `WorkoutReplacementPatch = WorkoutMetadataPatchInput & { exercises }` with all metadata optional, so missing title → `Predicate.isString(title)` fails and missing timestamps → `normalizeFetchedWorkoutTimestamp(undefined)` throws `WorkoutPayloadError` (`mutation-semantics.ts:~360-366`). It fails loudly rather than corrupting, but it's a regression vs main where fetched values were preserved.
Fix: (a) restore the `?? null` default for omitted description; (b) either require title/start_time/end_time on the replacement input schema or fetch the current workout in the replacement branch as main did.
