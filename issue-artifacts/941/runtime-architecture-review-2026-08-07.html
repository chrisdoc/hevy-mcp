Architecture review Snapshot 2443cad 7 August 2026 Read-only

One deep application spine.
Three honest runtime hosts.

The repository already has the right macro-shape. The best architecture is to deepen the runtime-neutral operation and capability modules, then keep Node stdio, Node HTTP, and the Cloudflare Worker as independent adapters with their own lifecycle, authentication, and state.

Top recommendation

Finish the shared operations kernel; do not add a universal runtime base class.

The first bounded slice should centralize endpoint policy, then continue operations domain by domain.

Decision in one minute

Preserve the seams that are real

  • Deep shared modules: Hevy client mechanics, endpoint/execution policy, domain operations, capability semantics, and MCP projection.
  • Concrete adapters: Node stdio, stateful Node HTTP, stateless Worker HTTP/OAuth, and CLI presentation.
  • Shared semantic events: safe tool, cache, request, and outcome observations; exporters remain runtime-specific.
  • No transport unification: stateful sessions and process shutdown are not the same problem as isolated Worker requests.
This report deliberately stops before concrete TypeScript interface design. Candidate selection comes first.

01

Complete the operations and capability kernel

Strongest

Turn the one-operation pilot into the application module that owns Hevy intent and policy across MCP and CLI.

Files and evidence

  • packages/operations/src/index.ts:18-29 — only workouts.list.
  • packages/operations/src/workouts.ts:10-101 — the entire production implementation.
  • packages/core/src/tools/* — 13 direct client call sites versus one operations call.
  • packages/cli/src/commands/index.ts:97-448 — most orchestration still bypasses operations.
  • Existing owner: issue #872.

Problem

Expected absence, pagination, search, mutation semantics, and composite workflows still live in presentation modules. The operations module is too shallow to justify its seam under the deletion test.

Direction

Migrate vertical domains incrementally. Operations owns intent-level normalization and outcomes; core owns MCP schemas and response presentation; CLI owns parsing and rendering. Delete superseded policy and tests as each slice lands.

02

Create one endpoint-policy vocabulary

Best first slice

Centralize endpoint identity while keeping retry, absence, diagnostic safety, and metric identity as distinct facts.

Files and evidence

  • hevy-client-kubb.ts:137-186 — safe, expected-404, and dynamic endpoint lists.
  • packages/core/utils/hevy-error-policy.ts:7-66 — overlapping read/list/mutation sets.
  • packages/core/utils/error-policy.ts:99-149 — safe codes, endpoints, and source identities.
  • packages/node/utils/hevy-client-observability.ts:19-45 — another endpoint normalizer.
  • Current routing owner: issue #937.

Problem

An endpoint change can drift among retry behavior, expected absence, privacy-safe diagnostics, operations behavior, and metric labels. A broad allowlist would be dangerous because those facts have different security and product meaning.

Direction

Give canonical endpoint identity one neutral owner and let each policy consume explicit facts. Unknown endpoints remain fail-closed. This is a bounded prerequisite for deepening operations and aligning observation.

  • High change leverage with a small first migration.

03

Deepen each runtime host without merging them

Strong

Improve locality inside Node and Worker while keeping three concrete transport lifetimes.

Files and evidence

  • packages/node/src/index.ts:303-497 — duplicated stdio/HTTP lifecycle policy.
  • packages/node/utils/streamable-http.ts:231-494 — stateful sessions, admission, disconnect, cleanup.
  • packages/worker/src/worker.ts:323-566 — stateless exchange plus raw-key/OAuth routing.
  • packages/worker/src/worker-oauth.ts:328-540 — OAuth grant and authorized request path.
  • Existing owners: #878 Node, #879 Worker, #876 protocol serving.

Problem

Node repeats startup, telemetry, failure classification, cancellation, and shutdown between stdio and HTTP. Worker normalizes origin/config more than once across raw-key and OAuth branches. A cross-runtime base class would hide rather than solve these differences.

Direction

Use one private Node lifecycle owner around two transport adapters. Use one Worker request-normalization owner before two auth adapters and one authenticated MCP exchange. Share only the primitive factory and neutral outcome vocabulary.

Guardrail

Do not make Node stateful sessions and Worker stateless requests implement one universal lifecycle. The official SDK and Cloudflare guidance explicitly support different deployment modes.

04

Close the Worker observation seam

Strong targeted move

Keep one safe semantic event vocabulary while projecting it through runtime-native sinks.

Files and evidence

  • packages/core/src/observation.ts:53-127 — privacy-safe tool observation interface.
  • packages/core/src/utils/cache.ts:10-32 — cache observation seam.
  • packages/node/src/index.ts:264-277 — Node wires tool, cache, and client observers.
  • packages/worker/src/worker.ts:220-244 — Worker passes only client logging.
  • cloudflare.config.ts:20-53 — platform observability is enabled.
  • Related owner: issue #928.

Problem

The Worker has request-level logs and platform traces, but no application-level tool, cache, retry, or Hevy-call correlation through the existing neutral interface. “No Worker observability” would be inaccurate; semantic parity is the gap.

Direction

Implement a Worker-native adapter over existing bounded observations. Keep Sentry and Node OTel packages out of the Worker graph. Exporters may differ; event meaning and privacy rules should not.

05

Separate Node embedding from executable startup

Worth exploring

Make the published programmatic interface safe to import without installing global telemetry providers.

Files and evidence

  • packages/node/src/index.ts:1-37 — telemetry import must execute first.
  • packages/node/utils/telemetry.ts:107-217 — import-time Sentry/OTel global setup.
  • packages/node/src/index.ts:293-301 — public builder performs a network validation probe.
  • packages/node/README.md:184-199 — published embedding contract.
  • packages/node/tsdown.config.ts:58-99 — library and CLI share the same source graph.

Problem

The public library entrypoint and executable composition share import-time telemetry. An embedding application can therefore acquire global providers and network behavior merely by using the builder. This weakens locality and makes the interface shallower than its documentation suggests.

Direction

Separate a side-effect-free embedding entry from the executable bootstrap. The executable explicitly initializes telemetry, environment config, update checks, and process lifecycle before running the chosen transport.

Why not first?

This materially improves the public Node interface, but it does not resolve the larger shared-policy duplication. Coordinate it with Node lifecycle work rather than creating a second runner.

06

Prove the seam with one runtime contract matrix

Required proof

Exercise the same primitive catalog and outcome semantics through core, Node stdio, Node HTTP, and Worker HTTP.

Files and evidence

  • tests/integration/mocked/* — broad core contract coverage.
  • tests/integration/worker-http.integration.test.ts:504-705 — representative Worker coverage.
  • packages/node/utils/streamable-http.test.ts — stateful host behavior.
  • packages/worker/src/worker.test.ts:383-440 — fresh server/transport per Worker request.
  • Existing owner: issue #880.

Problem

Adapter tests prove local mechanics, but parity of every primitive, schema, safe outcome, and protocol era is not yet one generated contract. A seam with three runtime adapters needs interface-level proof.

Direction

Generate behavior cases from accepted capability descriptors, execute them through each supported host, and keep host-specific lifecycle tests separate. Tests consume the model; they do not redefine it.
